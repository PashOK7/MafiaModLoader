## Follow-up: a matching native write fingerprint

The owner reports entering a car, changing camera, then returning to the main menu.
The dumped car model is `Models\PONTFOR01.i3d` (Crusader Chromium Fordor, color 1).
The initial controlled run used another traffic car without the camera change and reached
the menu; it is not evidence against a rare failure. All 92 files in the current owner
save directory were copied and hash-verified before the follow-up (`owner-save-pretest/`).

Comparing the failed model with its intact paired model gives three differing dwords before
the linkage fields: +0 = 0, +0x10 = 0x80000000, +0x44 = 0x14. The allocation header at -8/-4
also contains 0/0x80000000. The immediately preceding 0x168-byte allocation is another skid
model, already destroyed by the reverse cleanup loop; adjacency alone does not assign blame.

`I3D_frame::UpdateMatrix` (1.0 LS3D+1A4A0, exact 1.2 twin +1A6E0) writes flags |0x14 at
receiver+0xAC and scaled quaternion-derived matrix rows at +0x50..+0x78. A receiver at
`0x172B2D40 - 0x68 = 0x172B2CD8` explains every observed changed dword, including the two
allocation-header words and their exact negative-zero bit patterns. It lies at +0x100
inside the preceding model, not at the start of a live frame.

The ignored `matrix_fingerprint.py` runs this exact native routine on a disposable buffer
holding captured bytes, with the three model fields restored from the intact neighbor and
two header sentinels. The output matches the entire captured 0xB0-byte buffer, with a balanced
call stack. No live model or heap header is modified by that fixture. This is a reproducible
write fingerprint, not yet proof of the original caller or why it supplied that receiver.

`UpdateWMatrixProc` (1.0 +1C570, 1.2 +1C7D0) inlines the same local-matrix calculation.
For the inferred receiver, its parent at +0x120 is the model's bounding-box value 0x5A0E1BCA.
It would fault reading that supposed parent's flags after writing the local matrix, before
setting the world-valid flag. A caller's exception guard can therefore hide a failed matrix
read while leaving these writes behind. This alternative must be traced too.

An isolated temporary `matrix_probe` diagnostic hooks both native routines, records callers
and receiver bytes when its first word is not an LS3D vtable, and blocks that invalid write.
It is not a shipped repair. It was built under the ignored incident directory and hot-loaded
in owner PID25244, with its manifest disabled by default. The ordinary host/mod binaries
are unchanged. The dumped car's frame name is `Corle auto0`, confirming native traffic
takeover rather than an ordinary spawned car. The next task is to capture the producer of
an invalid receiver, including that takeover and the preceding taxi-to-menu-to-Pauli load.

## Confirmed producer: a stale HUD car reference

In owner PID25244 after taxi-to-Pauli loading, `world.near` returned no actors even for type 2
(the live player). This was a tool defect, not absent traffic or an inactive mission script.
The HUD car slot `0x658330 + 0x94A0` still held `0x0FEB6A88`, already unreadable. NearActors
adds LastCar without lifetime validation; its single exception guard discards the whole result.
Clearing just that borrowed reference through native RadarSetPlayerCar restored 13 nearby cars.

The temporary `matrix_probe.hud_fixture` command substitutes disposable actor/frame buffers for
the HUD reference for one synchronous SDK world_near call, restoring the slot in a finally block.
The fake frame has an invalid parent, so native world-matrix calculation writes the local matrix
and then faults inside NearActors' guard. It returns count 0 after one matrix call, with the same
victim-relative values as the dump: +0 = 00000000, +0x10 = 80000000, +0x44 = 00000014.
Only that disposable receiver is exempted from the diagnostic guard. No live object is corrupted.

The native RadarSetPlayerCar setters were checked in both builds: 1.0 `0x54C620` writes HUD+0x94A0;
1.2 `0x5FA500` writes HUD+0x44A8. Native actor removal and return-to-menu tests both leave the
borrowed pointer behind on the pre-fix loader in both labs. world.remove already cleared its own
spawned cars, so it did not cover native deletion or mission teardown.

The host repair clears the HUD reference before mission shutdown and when its exact actor is
destroyed, before mod destruction callbacks. A different actor's destruction preserves the live
last car. `tests/game/test_last_car_lifetime.py` covers these boundaries using native removal.
Both native lab builds pass all four lifetime assertions with the repair (exit 0), including
preserving a different live car. The complete x86 build, offline suite and MCP smoke pass, exit 0.
Receipts: `native-hud-fix.log`, `offline-hud-fix.log`, `mcp-smoke-hud-fix.log` in the incident folder.

Regular host SHA-256 is now `BD3BD3C4F6C84B8CFB9F624E5D74CDE914656EB6026BA2DDBE8A5B98FE22A098`;
matching PDB `FDDF77F351C63105CA4C58C547311D38039703E2AD8CB100B0D741D42EA284C6`.
The pair is hash-verified in both labs and the owner copy, with preimages in `pre-hud-fix/`.
Owner PID13852 used the regular host and original soundscape/draw_probe/ragdoll set: taxi save5,
return to menu, Pauli save510. The HUD slot is zero after taxi close and after Pauli load;

This establishes a real producer and a matching deterministic corruption mechanism. The original
