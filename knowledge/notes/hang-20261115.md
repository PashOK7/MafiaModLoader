  before opening its memory. Both labs were stopped. The process was nonresponsive but still alive;
  bridge status/where timed out. A bridge timeout is not proof that the process exited.
- Loaded host34B23E81... / PDB8ADADD9F... and ragdoll5505A21D... / PDB2AA04C5D... . The copy was not
  replaced by the recent source publication. The installed/live module names and hashes are retained.
- Owner was winding up a grenade throw. Earlier play included gunfire, car explosions and ragdolls.
  This is context, not proof that the throw caused the fault. No route replay was requested.
- Log stops at12:01:51.691 with the guarded Jolt step failing and an attempted world reset. At12:01:51.692,
  the host reports a ragdoll callback access violation in event2 (mission tick).
- All evidence is ignored under build/hang-20261115-120151. An elevated read-only collector saved three
  x86 snapshots, including a567,742,506-byte full-memory dump; log/trace copies, binary hashes and
  SHA-256 receipts are retained. No game input, window activation, game-memory writes or termination.

## Confirmed failure sequence

1. `SafeJoltStep` returned false, so TickBody entered the existing recovery branch. The original
   exception behind that return was swallowed by `Guarded` without retaining its context.
2. Recovery called `jolt_ragdoll::Clear`. The host's saved16-frame fault stack resolves through
   clearing Entry records, JPH::Ragdoll destruction and a SwingTwistConstraint deleting destructor,
   then `_aligned_free`, `RtlFreeHeap` and `RtlpFreeHeapInternal`.
3. The recorded access violation is at x86 ntdll+0x60412, `RtlpInterlockedPopEntrySList+0x22`:
   reading the next link through invalid address0xE259F0EE. This is a later cleanup exception,
   not a captured explanation of the earlier failed simulation step.
4. The host's NoteFault retained that stack and Faulted wrote the short error line. Faulted then
   attempted `json::array`, allocating12 bytes through its operator new/RtlAllocateHeap.
   The main thread is waiting in the allocator's SList helper on an exclusive SRW lock.
5. In the full dump that lock is ntdll+0x124F98 (absolute0x77B44F98), with locked/waiting bits set.
   The faulting SList helper acquires that lock before its failing link read. Several new threads
   also wait in allocator calls while initializing; the game cannot reach its next frame/unload.

The three x86 snapshots have identical main PC/SP/BP and the same retained fault stack. The process
remained nonresponsive during inspection. This establishes the immediate allocator/recovery/diagnostic
hang. It does not identify which earlier writer damaged allocator state, a specific constraint allocation
as that writer, or the original guarded Jolt exception. Do not relabel it as the November14 Ogg load deadlock.

## Limits and a discarded lead

A residual exception-shaped record on the main stack describes a write at ntdll!RtlpSubSegmentInitialize
to0x14009000. Its adjacent context was overwritten by formatted log text. Its timing and relationship to
the guarded step are unproven. It is not accepted as the primary cause or used to infer a source fix.

Main/host/ragdoll symbols were matched to the retained installed PDBs. The exact Windows x86 ntdll PDB
was fetched through tools/fetch.py from Microsoft's symbol server and accepted by the debugger for the
dump's image. Detailed debugger output and the SList disassembly remain local. The first64-bit Python
snapshots preserved WOW64 native contexts unsuitable for the intended x86 walk; the later native x86
collector supplies the usable stacks. The malformed command-line debugger attempts are retained too.

## Consequences for recovery and next diagnosis

- Catching an exception does not establish that the process heap is usable. Current Faulted performs
  dynamic allocation, so even the fault-report/unload path can hang after heap-internal failures.
  Another catch around Clear or JSON would not repair an abandoned lock or corrupted heap.
- Preserve the FIRST guarded-step exception before cleanup. A bitness-matched external first-chance
  capture can retain its actual context while all target threads are stopped, before rollback/logging
  overwrite the evidence. This still need not identify an earlier silent memory writer.
- Identify the writer with targeted, controlled allocation/lifetime validation once that first operation
  is known. Do not tune physics, blame the grenade/EAX or promise that another random playthrough proves a fix.
- No production change, binary installation or process termination was made in this inspection.
  The user's frozen process was left intact; the captured evidence does not depend on keeping it alive.
